# Join 性能基准复测

## 修正内容

本记录替代此前的性能表。旧基线额外统计释放次数，而优化版没有；旧阶段驱动还
重写了物化循环，遗漏原实现的临时 Vec 和 row_hit。旧耗时比例与阶段对比因此撤回。
本轮与上一轮都直接使用两版原始核心源码，不手写“基线 Join”；上一轮采样保留在
文末，本轮增量采样列在前面。

改动。修改前已经把当时工作树的 `src/join.rs`、`src/model.rs` 固定保存到

### 本轮解读与限制

- A 表预估与实际 probe 现在共用一个 `String`：每行先 `clear`，再把类型前缀、
  数字格式和文本正文直接写入，最后以 `&str` 查询。括号扫描在确有替换时也
  直接写入该缓冲区；trim 只借用切片。首次分配和遇到更长 key 时的容量增长仍
  会分配，因此不能把整个 Join 宣称为零分配。
- 分配减少最稳定地出现在 A 侧被扫描两次的展开场景：例如 100k 唯一键从
  700,025 降到 500,026 次请求；无展开只扫描一次，所以 u1m 场景仅减少约 6%。
  输出行、右表索引和 CellValue 物化仍然会分配；本轮数字是实测，不是理论收益。
- `high_500k_bracket_100_expand` 当前慢 1.2%，且三次范围有波动；这说明该场景
  的总耗时主要由 B 索引/输出物化构成，不能把括号路径的直接写入宣传成必然提速。
  RSS 中位数基本不变，拒绝路径也保持实际输出 0、预估 10000000；这不是内存
  下降保证。
- 没有混入类型化键、零分配 HashMap probe、更换 hasher、延迟物化或结果视图重构。
  复合键 U+0001 分隔符仍不转义，编码碰撞行为由既有回归测试保持；`001` 与数字
  `1`、`Empty` 与文本空串/纯空白的既有区别也未改变。

## 上一轮完整复测（历史：f6bd822 → issue #1 第一轮）

下面保留上一轮完整 release 基线和原始采样，不能用来归因本轮缓冲区优化。
上一轮脚本曾从 Git 提取 `f6bd822`，当前脚本已改为读取上面的本轮快照。

### 当时的可复现方法

```bash
./scripts/bench-join.sh
# 指定场景：
./scripts/bench-join.sh u100k_exact_narrow_100
```

- 日期：2026-09-10。平台：WSL2 Linux x86-64，AMD Ryzen 7 3800X，16 个逻辑处理器；
  rustc 1.98.1 (48a229cea 2026-09-01)。这是本机合成数据结果，不代表 Windows/arm64 性能。
- 当时基线固定为 `f6bd8229501be9411983d614c39bd54921796ada`。历史脚本通过 `git show` 提取
  `join.rs` 和 `model.rs`，当前版复制工作树对应文件。两版均用同一个 rustc、
  `--edition=2024 -O` 编译为仅含核心模块的库，再编译同一个 `scripts/join_bench.rs`。
  无需 GUI 依赖，不切换工作树，不联网；本地需要保留基线提交。
- 基线调用原始预估函数再调用原始 join；优化版调用 join_with_limit 复用索引。
  两版均仅在开启重复展开时执行 500 万行预检，计时包含完整预检及 Join 调用，
  不包含输入生成、结果验证和返回结果的释放。
- 纯计时二进制使用默认系统分配器，不安装计数分配器，不做逐行时钟采样。
  每场景两版各运行三个独立进程，交替先后顺序，表中给出中位数和最小–最大值。
  不在同一进程内预热；只有三个样本，不能据此给出统计显著性结论。
- 分配统计使用另外编译的计数二进制，各运行一个独立进程；两版共用完全相同的
  alloc/realloc 统计，dealloc 均直接转发。计数运行的耗时不用于性能结论。
  累计请求字节包含 realloc，不是存活内存。纯计时日志中的分配数 0 表示未采集。
- RSS 取三个纯计时进程峰值的中位数，包含输入、结果和计时后验证的内存；
  每进程只执行一次 Join，不再包含第二次诊断 Join，不能与旧 RSS 表直接比较。
- 计时结束后根据数据生成规则独立验证输出行数、内容、A/B 顺序、row_hit、
  left_matched、right_matched_rows 和拒绝行为。成功路径不为了打印“预估行”额外扫描；
  日志 None 表示未单独取得预估值，不代表 0。
- 脚本打印临时目录，保留两版源码、驱动、编译产物、环境和各次原始输出。
  本次逐次采样保存在 [CSV](join-benchmark-samples.csv)，可直接复算下表。

### 上一轮解释与限制

- 分配次数和累计请求字节明显减少，纯耗时也在本次场景中下降；无法从整体对比
  推断每个单独优化贡献了多少，也未测量导出提速。导出借用结果表是代码层面的复制消除。
- `high_500k_expand_reject` 两版都预估 1000 万行并拒绝。优化版提前保存完整行号索引，
  拒绝路径的 RSS 仍比仅保存次数的基线高；这是索引复用的已知权衡。
- 基线预估漏算 Left 未命中行，如 d10_500k 场景预估 50 万但输出 55 万。
  当前预估修复由核心单测验证；本次成功样本的预估差异均未改变拒绝决策。
- 名称 bracket_100k_exact_75 表示数字文本宽松开关关闭，但括号归一化开启，
  不是 KeyMode::EXACT（两个开关全关）；其他括号场景也只开启括号归一化。
- 不再发布基线/优化版的分阶段对比：旧预估包含计数表构建，无法与新预估探测直接
  对齐。核心已有的 join_with_limit_metrics 仅作当前实现的诊断接口；其逐行采样
  有开销，不能替代这里的纯耗时，也不用于证明某阶段优化收益。
- Cow 只消除正文无需变化时的额外复制，规范键仍有字符串分配。类型化键、
  零分配 probe、更换 hasher、延迟物化未实施，仍需单独测量和设计。
- 已知复合键分隔符碰撞保持原有行为，由回归测试和注释明确记录。
